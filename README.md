# JR West Super TID

JR西日本 東海道・山陽本線（琵琶湖線／JR京都線／JR神戸線、姫路〜上郡）と、
湖西線・JR宝塚線（福知山線）・JR東西線・学研都市線（放出〜木津）・赤穂線（相生〜播州赤穂）の
運行を再現した TID シミュレーター。

`index.html` をブラウザで開けば動きます（サーバー不要）。

## 公開先

GitHub Pages で公開しています。PCの電源が入っていなくてもアクセスできます。

**https://wata9857-ops.github.io/tid-simulator/**

`main` ブランチに push すると、1〜2分で自動的に反映されます。
（GitHub の Settings → Pages が「Deploy from a branch: main / (root)」になっています）

### 公開する前に必ず走らせること

```
node tools/stamp_version.js        # js/css の URL に版の印を付け直す
```

GitHub Pages は js / css を `Cache-Control: max-age=600` で配ります。
「読み直して確かめてね」の指定が無いので、一度開いたブラウザは
しばらくサーバーに問い合わせずキャッシュを使います
（iOS / iPadOS の Safari はさらに長く持ち続けることがあります）。

そのため、URL を変えずに中身だけ差し替えると

* HTML は新しい / js は古いまま

という組み合わせが起きます。これがいちばん分かりにくい壊れ方で、
**新しいボタンは出ているのに押しても何も起きず、JavaScript のエラーも出ません。**
実際に一度これをやってしまいました（下の「やってしまった失敗」を参照）。

`tools/stamp_version.js` は、読み込む URL に中身から作った印を付けます。

```html
<script src="js/40-tid-theme.js?v=56df0e8d"></script>
```

中身が変われば印が変わるので、キャッシュを持っているブラウザでも
必ず読み直されます。走らせ忘れは `node tools/check_refs.js` が見つけます。
さらに HTML の末尾に見張りを置いてあり、万一
「必要な部品がそろっていない」状態で開かれたときは、
一度だけキャッシュを避けて読み直します。

### やってしまった失敗（2026-09）

「線路図の倍率を変えた」「拡大縮小を付けた」「編成検索を付けた」と報告したのに、
公開先ではどれも効いていませんでした。原因は上のキャッシュです。

検証が見逃した理由もはっきりしています。
Playwright の `browser.newPage()` は**毎回まっさらなキャッシュ**で開くので、
「前に開いたことのある端末」の状態をまったく再現できていませんでした。
HTTP 200 が返ること・ボタンが DOM にあることだけを見ていたのも誤りでした。

いまは `tools/check_cache.js` が、
GitHub Pages と同じ応答ヘッダのサーバーで
「旧版を読み込ませる → 新版に差し替える → 同じブラウザで開き直す」
を再現し、新しい版がちゃんと効くかを確かめます。

外部ライブラリもビルドも使っていない素の HTML / CSS / JavaScript なので、
GitHub Pages にそのまま置くだけで動きます。

### iPad で表示できるかの確認

線路図は横 31,160px の巨大なキャンバスに描いています。

## 編成（車両）の運用規則

割り当ての規則は `js/06-fleet.js` の `FleetManager.profileFor()` に集約しています。
規則を変えたいときはここだけ直せば全体に反映されます。

* 新快速は必ず **12両（8両＋4両）**。網干総合車両所の 223系／225系のみ。
* 新快速・快速に **221系／207系／321系**（221系性能の6000番台を含む）は使わない。
* 湖西線の**普通**は京都支所の **221系または223系**のみ。
  （湖西線経由の新快速・快速は網干の223系／225系）
* 京都支所の車両は本線（JR京都線／JR神戸線）の運用には入れない。
* **JR東西線内**を走る列車は **207系または321系**のみ（快速も含む）。
* JR宝塚線から**大阪方面**へ直通する列車は **223系または225系**
  （宮原支所の6000番台を優先）。
* 米原〜敦賀間と湖西線を除き、普通以上の種別は **6両以上**。
  足りないときは実際の組成にあわせて増結する（207系は4+3、223系などは4+4）。
* 留置されている編成の編成番号は、起動ごとにシャッフルして割り当てる。

### 車両所グループ

編成データの `g` で持ちます。文字列の照合ではなくこの値で判定します。

| g | 車両所 | 略号 | 主な形式 |
| --- | --- | --- | --- |
| `ABOSHI` | 網干総合車両所 | ホシ | 223系1000/2000番台、225系0/100番台 |
| `AKASHI` | 網干総合車両所明石支所 | アカ | 207系、321系 |
| `MIYAHARA` | 網干総合車両所宮原支所 | ミハ | 223系/225系6000番台 |
| `KYOTO` | 吹田総合車両所京都支所 | キト | 221系、223系2500/6000番台 |

### 在庫が足りないとき

1. 指定の留置場に条件を満たす編成がなければ、近い留置場から順に借り出す
   （`FLEET_MAX_BORROW` 箇所まで）。
2. それでも足りないときだけ、車両所ごとに `FLEET_RESERVE` で決めた本数だけ増備する。
   **上限があるので無制限には増えません**（現状の設定では合計28本まで）。

## 運転本数と速度（実際の時刻表に合わせる）

本数は `js/10-timetable.js` のパターンダイヤが決めます。同梱の駅時刻表
（`osaka1.pdf` ほか、Yahoo!路線情報／JRおでかけネットの駅時刻表）から
平日の1時間あたり本数を写し、実際と同じ「毎時同じ分」に発車させます。

### 直した点

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| 昼間に新規生成が止まる | 在線本数の上限 220本が、必要数（230〜250本）より少なく、11時以降ずっと上限に張り付いていた | 上限を 430〜520本に。本数はパターンダイヤが決め、上限は暴走時の保険にした |
| 普通ばかりで快速・新快速が走らない | 生成間隔を係数の掛け算で決めていた（普通は ÷3.0、新快速は ×1.5 など）／新快速に「18本まで」の決め打ち上限 | 時間帯ごとの本数を直接指定。上限は時刻表から出した値に |
| 混雑すると生成が止まる | 「同じ種別が前後2駅以内に2本いたら作らない」という大まかな判定 | 着発線の空きと、進行方向すぐ先の閉塞の空きという実際の条件に |
| 折り返しで偏りが残る | 折り返しは種別を変えないので、朝の偏りが一日続く | 種別ごとの在線本数の目安を超えたら、折り返さず入区させる |
| 列車が線路に居座る | 1閉塞の基本時間が 普通75秒・他60秒＝1駅あたり実際の1.3〜1.7倍。減速が重なり実測は3〜5倍 | `BLOCK_RUN_SEC` を実際の表定速度から決めた（普通48秒／快速40秒／新快速34秒） |

### 在線本数の目安が効いていなかった問題（2026-09 に修正）

`TT_ACTIVE_BUDGET`（種別ごとの在線本数の目安）は前からありましたが、
2か所の抜け道があって、まったく効いていませんでした。

| 抜け道 | 何が起きていたか |
| --- | --- |
| 車両所からの出区計画 (`js/27-operations.js`) が目安を見ていなかった | 朝の2時間だけで普通が約100本、本線に出ていた |
| 目安を超えて「運用を終える」と決めた列車が、入区できないと `preferTurnback` でそのまま折り返していた | 決定が毎回取り消され、折り返しで走り続けていた |
| 西明石始発の増発 (`checkFixedSpawns`) が1日じゅう25分おきに素通しだった | どの駅時刻表にも対応しない列車が増え続けていた |
| 分岐線の目安が3線区の合計だった | 湖西線だけ実際の2倍以上でも抑えられなかった |

直したうえで、実測した発車本数が駅時刻表に合うように目安を詰め直しました
（本線 普通44 / 快速34 / 新快速30、湖西8 / 宝塚12 / 東西10）。
あわせて「折り返した先に続く列車がいないときは運用を終えない」
(`ttStillNeeded`) を入れ、間隔が開きすぎないようにしています。

### 効果（`tools/harness.js tools/check_timetable.js` で計測）

昼間 10〜16時の1時間あたり本数。「前」は 2026-09 の修正前。

| 指標 | 前 | 後 | 実際 |
| --- | --- | --- | --- |
| 大阪 上り 普通/快速/新快速 | 16.7 / 2.8 / 3.0 | 11.3 / 3.2 / 4.7 | 8 / 4 / 4 |
| 大阪 上り 合計 | 27.3 | 24.3 | 22 |
| 大阪 下り 普通/快速/新快速 | 11.5 / 1.8 / 3.3 | 7.0 / 3.0 / 3.8 | 4 / 4 / 4 |
| 西明石 上り 合計 | 17.7 | 16.5 | 13 |
| JR宝塚線 下り 合計 | 7.8 | 8.8 | 9 |
| JR東西線 下り 合計 | 10.8 | 10.8 | 8 |
| 湖西線 普通 | 6.7 | 4.2 | 3 |
| 昼間の在線（本線 普通） | 124〜137本 | 69〜78本 | 目安 44本 |
| 昼間の在線（全体） | 255〜260本 | 197〜205本 | — |
| 1駅あたり所要（普通） | 5.3分 | 4.6分 | 2.8分 |
| 60秒以上進めない列車 | 11.6% | 5〜9% | — |

大阪の上り内側線で、普通どうしの続行間隔を測ると
（`tools/harness.js tools/check_density.js`）

| 指標 | 前 | 後 |
| --- | --- | --- |
| 中央値 | 3.25分 | 3.75分 |
| 最短 | 1.00分 | 2.25分 |
| 2分未満の続行 | 93本中 15本 | 66本中 0本 |

普通は1駅あたり約4.6分かかるので、前は「1駅より近い間隔」で
続行している列車がふつうにありました。いまは最短でも2.25分空きます。

混雑を抑えるのに、列車を消したり生成確率を下げたりはしていません。
着発線の空き・閉塞の空き・続行間隔という実際の条件で発車を抑え、
走りすぎている種別は運用を終えて車両所へ戻します。

分割前の `index.html` にあった運転整理の仕組み（自動抑止、協調型追従による
減速、優先順位による待避、間引き・折り返し、混雑時の行先変更）は
`tools/check_logic_diff.js` で確認したとおりそのまま残してあります。

## 配線（線路・番線・待避線）

配線略図（`スクリーンショット (690)`〜`(712)`、haisenryakuzu.net）が
物理的な配線の正解です。`tools/extract_haisen.py` が図を画素から読み取り、
`tools/check_topology.js` が実装と突き合わせます。

```
python tools/extract_haisen.py 692                 # 駅ごとの線路・待避線・ホームを数える
python tools/extract_haisen.py 692 --at 1740       # x位置の縦断面
node tools/harness.js --tid tools/check_topology.js  # 実装と図の照合
```

### 直した点

* **待避線が無かった** … 石山・膳所には外側線のさらに外側に待避線があります
  （配線略図で本線4本＋待避線2本）。線路図に描くだけでなく、外側線の
  2本目のレーンとして持たせ、列車が実際に入れるようにしました。
* **複々線の外に内側線があった** … 内側線（電車線）があるのは西明石〜草津だけです。
  それ以外の全線にも内側線のブロックを作っていたため、配線略図に無い線路が生まれ、
  そこへ入った列車が「線路の無い場所」を走り、駅の番線と線路の数が
  46駅で食い違っていました。湖西線などと同じくプレースホルダにしました。
* **番線が存在しない線路に付いていた** … 加古川・大久保・東姫路などの複線区間の駅で、
  番線が内側線の座標に割り当てられていました。上下線に割り当て直しました。
* **石山の渡り線** … 上り外と下り外を直接つなぐ形になっていましたが、
  複々線の中の駅なので、あいだの内側線2本を飛び越す線路は存在しません。
  外側線と内側線をつなぐ形に直しました。

### 番線（のりば）の出しかた

番線は `js/03-stations.js` の `stationLaneMap()` が一元的に決めます。
`(駅, 線路ID, レーン番号) → 番線` の対応表を作り、Super-TID の線路図・
駅の在線表・列車情報・発車標がすべてこれを見ます。

* 以前は `rule.labels[レーン番号]` と引いていたため、どの線路でも `labels[0]` になり、
  4本の線路すべてが「1番線」と表示されていました。
* 発車標は `(レーン番号 + 1)` をそのまま出していて、配線と無関係でした。
* 駅間にいる列車には番線を出しません（`trainPlatformLabel()` が null を返す）。
* レーンが余っている駅は待避線として自動で名前を付けるので、
  「番線名の付いていないレーン」は全駅で 0 です。

### まだ終わっていないこと

配線略図は33枚あり、駅ごとの転記は途中です。`tools/check_topology.js` の
`REF` に書いた駅（膳所・大津・瀬田・南草津・石山）だけを図と照合しています。
`REF` に駅を足せば、そのまま検証対象が増えます。

### 実物と同じにした描き方

* **左右の向き** … 画面の左が米原・草津方（上り方）、右が大阪・姫路方（下り方）で、
  下り列車が左から右へ進みます。シミュレーターの内部座標は逆向きなので、
  線路図を描くときだけ `tidX()` で入れ替えています（内部座標は変えていません）。
* **ホーム** … 島式ホームは「面している2線のちょうど中間」に黄色い帯を1本描き、
  上の線路の番線番号を帯の上、下の線路の番線番号を帯の下に書きます。
* **番線番号** … 駅ごとに実物の並びが違います。膳所・大津・向日町・塚本は
  下り外が4番、吹田・西大路は下り外が1番です。京都は1番のりばが無く
  0番と2〜10番、山科は外側線にホームが無く内側線が2番・3番です。
* **信号** … 実物には灯を並べた信号機の絵はありません。進路が開通している区間を
  黄緑に塗り、停止現示の場所に赤い四角を置いて表します。
  注意・警戒現示は軌道回路の丸を黄色で囲みます。
* **在線** … 線路そのものは塗りません。列車の位置の丸の色で示します。
* **発着予告** … 駅ごとに「その線路に次に来る列車」を、線名の小札と
  両端のホームを表す黄色を付けた札で出します。下り線は駅の右、上り線は駅の左に
  並べるのも実物と同じです。

### 実物と違うところ（理由つき）

* **駅の間隔** … 実物は駅ごとに幅が違い、京都のように大きい駅は広くとっています。
  この線路図は全線 150駅ぶんを同じ座標系（`blk.x`）で描いていて、
  その座標は運行の処理と旅客向け画面が共有しているため、等間隔です
  （1駅 360px × `TID_SCALE` 1.3 ＝ 468px）。
  足りないときは画面の拡大縮小（後述）で拡げられます。
* **軌道回路の数** … 実物は駅間に10個ほど境目がありますが、ここでは
  シミュレーターの閉塞（1駅 3ブロック）の境目をそのまま丸にしています。
  見た目のために丸を足すと、在線・信号の位置が閉塞と食い違ってしまいます。
* **湖西線の位置** … 実物は山科で湖西線の2線を本線のあいだに挟んで描き、
  1番・4番のりばを与えています。この線路図は全線を1枚で見せるため、
  湖西線・JR宝塚線・JR東西線は本線の下に別の帯として並べています。
* **編成番号** … 実物の札には編成番号が入りませんが、
  どの編成が運用に入っているか分かるように車両所ごとの色帯で足しています。

### 駅の中の配置（2026-09 に描き直し）

実機の画面（`IMG_0332.PNG` / `IMG_0333.PNG`）で、渡り線がホームの帯と
「N番のりば」の札を斜めに突き抜けていました。実物の Super-TID は
駅をこの順で描きます。

```
本線 ─ 転てつ器 ─ 斜めの取付線 ─ 着発線(枠付き) ─ 斜めの取付線 ─ 転てつ器 ─ 本線
          └ 渡り線はこの「のど」に置く。ホームの上は通らない。
```

直した点

* **渡り線を「のど」へ** … `tidThroatX()` が求める、着発線の枠の外側に置きます。
  両渡り (`"x"`) は実物の主要駅と同じく駅の前後に1組ずつ。
  `TID_JUNCTIONS` の4つめに `"L"`（画面の左＝米原方）/`"R"`（姫路方）/`"B"`（両側）
  を書くと、駅ごとに指定できます。
* **大きな駅だけ縦に広げる** … `tidStationLayout()` が、となり合う番線が近すぎる
  所だけ上下に振り分けます。広がったぶんは駅の入口・出口に斜めの取付線を描いて
  本線につなぐので、線路として筋が通った形になります（実物の京都駅も同じ形）。
  ホームを挟む2線は 38px、列車表示が向かい合う所は 76px 空けます。
  番線が11本ある新大阪だけは入りきらないので 32px まで詰め、
  そこでは編成番号の帯を表示の左に並べて高さを抑えます。
* **列車表示をホームと反対側へ** … 島式ホームの上側の線は上、下側の線は下に
  列車表示を出します。ホームの帯と番線札に重なりません。
* **番線の縦位置を配線データから引く** … `stationLaneMap()` に番線の番号
  (`index`) が入っていなかったため、線路図はずっと「線路の定位置から18pxずつ」
  という代替の計算に落ちていて、列車が番線と違う高さに描かれていました。
* **新大阪の番線** … 11本すべてが上り外に属する定義になっていました。
  上り2面4線・下り2面4線・おおさか東線ホームとして4本の線路に割り当て直しました。

### 番線とレーンの食い違い（2026-09 に修正）

札が重なる不具合を画素で測って追ったところ、原因は表示ではなく配線データでした。

「この駅のこの線路は何本のレーンを持つか」が `TrackManager.initBlocks()` の中に
書かれ、「番線の縦位置」は `stationLaneBaseYs()` に別に書かれていて、
**86駅中 23駅で食い違っていました。**

| 食い違い | 何が起きるか |
| --- | --- |
| 番線の定義のほうが多い（神戸・甲子園口・茨木・草津） | 縦位置の無い番線が黙って捨てられ、そのレーンの列車が「線路の描かれていない高さ」に出る |
| レーンのほうが多い（高槻・西明石・尼崎・米原など） | 余ったレーンが自動で足されるが、そこにも線路が描かれない |
| 尼崎（本線・宝塚線・東西線でレーンを共有） | レーン2・3の列車がどちらも「最後のレーン」に丸められ、2本が**まったく同じ高さ**に描かれる |

直し方

* レーン数を `stationMainLaneCount()` / `stationTrackLanes()` の1か所にまとめ、
  `TrackManager` も線路図も同じ値を見る。
  番線の定義のほうが多い線路は、そちらに合わせて線路を増やす
  （御着・東加古川・土山の中線など。番線の定義のほうが実物に近い）。
* `stationLaneSlots()` が「実際にあるレーンぜんぶ」の縦位置を返す。
  線路図もその全部を描くので、列車が線路の無い所に出ることが無くなった。
* 尼崎は `STATION_SHARED_LANES` として、上り側・下り側の通し番号で番線を引く。
* 島式ホームの組は「となり合う2本」だけにした。あいだに別の線路がある2本を
  組にすると、ホームの帯がその線路をまたぎ、番線の札が
  あいだの列車表示と重なる。
* ホームに面していない線の列車表示も、空いているほうへ出す。

結果（`node tools/check_overlap.js`、15駅 × 6時点 = 90回の測定）

| 重なり | 前 | 後 |
| --- | --- | --- |
| のりば札 × 列車表示 | 392px² | 0 |
| 列車表示どうし | 1872px²（尼崎で完全に重なる） | 0 |
| 縦位置とレーン数が食い違う駅 | 24 / 86 | 0 / 86 |

なお、書き起こしの足りない駅では、余った番線名をレーンへ順に当てています。
番線の並び順までは配線略図を写すまで保証できません
（`tools/check_topology.js` が転記の進み具合を出します）。
それでも「番線名が消える」「線路の無い所に列車が出る」よりは実物に近い形です。

### 北方貨物線が破線に見えていた不具合（2026-09 に修正）

本線は駅で番線がずれるので、その区間だけ線を空けて着発線のほうで描きます。
その「空ける場所」を線路IDから当てようとしていて、当てはまらない線路
（北方貨物線）では**本線の全86駅ぶんの穴**を空けていました。

いまは、穴を空ける場所をその線路が実際に持つブロックから取ります。
北方貨物線には本線の番線を当てはめません（途中にホームの無い複線なので）。
`tools/harness.js --tid tools/check_tid.js` が継続的に見ています。

### 線路図の拡大縮小（`js/43-tid-zoom.js`）

* 絞り込み欄に入れるとその場で一覧が短くなる

```
アカT08  207系1000番台 4両  網干総合車両所明石支所
```

### 指令連絡（`js/31-comms.js` / `js/45-tid-comms.js`）

現場（乗務員・車掌・駅長・保線区・信号通信区・車両所）から連絡が入り、
指令が答えを選ぶ仕組みです。**重要度で扱いを分けます。**

| 重要度 | 扱い | 例 |
| --- | --- | --- |
| minor | ほかの指令員が処理する。**画面には上げない**（記録には残る） | 続行間隔の照会／出区の可否／線路点検／ホーム混雑／乗務員交代／着発番線の変更／信号設備の確認 |
| important | 画面に上げる。**当該列車を抑止して答えを待つ** | 待避の可否／折り返しの判断／車内取り扱い／車内急病人／続行順序／遅れの波及／折り返し時間不足 |
| critical | 画面に上げる。抑止したうえで、答えが後続や番線にも及ぶ | 到着番線支障／車両故障 自力運転不能／線路支障／信号故障 場内不開通／番線の割り当て |

全19場面、うち12場面が指令に上がります。
何でもかんでも上げると細かい連絡に埋もれて、本当に判断が要る場面を
見落とします。実際の指令所でも、日常的な照会は当務の指令員が裁いています。

* **答えるまで動きません。** important 以上の連絡が入った時点で当該列車を
  その場に抑止します（`commIncidentHold`）。指令が答える前に走り出すと、
  判断に意味がなくなるためです。抑止は `resolve()` が必ず解くので、
  「抑止したまま忘れる」ことはありません。
* 時間が経つと**続報**（`followUp`）が入り、さらに経つと**催促**（`escalate`）が入ります。
* 文面は候補からその場で選ぶので、同じ場面でも毎回同じ文章にはなりません。
* 期限（important 210秒 / critical 150秒）内に答えないと、
  **別の指令員が引き取って処理します**。そのときの答えも重みつきの抽選なので、
  結果は1通りに決まりません。
* 旅客向け画面（`index.html`）では答える相手がいないので、すべて
  時間切れとして処理されます。つまり、これまでどおりの自動運転です。

18時間ぶん走らせた実測（`tools/harness.js --tid` のプローブ）

| 指標 | 値 |
| --- | --- |
| 指令に上げた連絡 | 78 件 |
| 当務の指令員が処理した細かい連絡 | 140 件 |
| 応答待ちの抑止中に列車が動いた回数 | **0 / 771 回の観測** |
| 取り残された抑止 | 0 |

**抑止は必ず `commHold()` を通すこと。** 指令の「駅で抑止」は指令が解除するまで
永久に止める作りなので、そのまま呼ぶと画面に人がいないときに抑止が溜まり、
主要駅のホームが埋まって線区全体が止まります（実際に、1駅あたりの所要が
8分＝実際の3倍まで落ち、大阪の下り列車が0本になりました）。
`commHold()` で掛けた抑止は、抑止駅に着いてから決めた秒数で自動的に解け、
抑止駅にたどり着かないまま時間が経った場合も取り消されます。

## 時間の進み方（倍率）

シミュレーション時間をゆっくり進められます。既定は **1.0倍**（従来の速さ）で、
0.9 / 0.8 / 0.7 / 0.6 / 0.5 / 0.4 / 0.3 / 0.25 / 0.2 / 0.1 倍が選べます。

* 旅客向け画面 … 指令パッドの「0. シミュレーション設定」
* Super-TID … 上のツールバーの「時間」

変えているのは **1Tick進めるのに待つ実時間だけ**です
（`js/23-game.js` の `stepMs = 1000 / CONFIG.timeScale`）。
1Tickの中身（`CONFIG.TICK_SEC` = 15秒）には触らないので、
1閉塞の所要時間・停車時分・抑止の秒数・時刻表・信号・運転整理の判定は
まったく変わりません。`CONFIG.TICK_SEC` を小さくする方法だと、
秒で書かれた全ての判定が狂います。

2つの画面を開いているときは、時間を進めるのは本体の画面なので、
倍率は指令（`js/28-dispatch.js` の `timeScale`）として共有します。

（`CONFIG.dayType`）。既定は平日です。

## 走行線路の規則（外側線 / 内側線）

複々線（西明石〜草津）には外側線（列車線）と内側線（電車線）があります。
どちらを走るかは `js/24-service-rules.js` の `serviceTrackSide()` が
**1か所で**決めます。

| 種別 | 走る線路 |
| --- | --- |
| 新快速 | 該当区間を通して **外側線** |
| 快速 | 平日朝の **高槻 → 大阪** だけ外側線。それ以外と土休日は **内側線** |
| 普通 | 内側線（電車線） |
| 特急・貨物・回送・臨時 | 外側線（列車線） |

参考（いまのシミュレーションでは使っていない過去の話）

* 新大阪駅の配線改良より前は、新快速が新大阪〜大阪だけ内側線を走っていた。
* 2006年3月17日まで、大阪発17時台の野洲行き快速が外側線を走っていた。

### 直した点

以前はこの規則が `checkLogicUpdates()` / `move()` / `checkHold()` の
3か所に別々に書かれ、食い違っていました。

| 症状 | 原因 |
| --- | --- |
| 新快速が京都から先で内側線を走る | 「朝ラッシュ以外は内側線へ転線」という条件が入っていた |
| 快速が朝以外・上り方向でも外側線を走る | 時刻で区切った独自の表（5:48〜8:36 など）が入っていた |
| 複々線の端で列車が往復して抜けられない | 西明石・草津で「内側線へ戻す」規則が、複線区間へ出る列車にも掛かっていた |

実測（`node tools/harness.js --seed=20260922 tools/check_convoy.js`、
複々線の中にいる列車を毎Tick数えたもの）

| 指標 | 前 | 後 |
| --- | --- | --- |
| 規則と違う線路を走っていた割合 | 6.77% | 2.25% |
| うち新快速が内側線 | 4968回 | 0回 |

残る2%ほどは「内側線が埋まっているので外側線へ逃がした」もので、
実際の運転整理と同じ動きです。

## 編成の瞬間移動をしない

行路表（`js/30-duty-log.js`）に

```
374M 京都 → 野洲     (野洲に到着)
470M 京都 → 野洲     (なぜか京都から始まる)
```

のように、終着駅と次の始発駅が食い違う行が出ていました。
編成が線路を走らずに移動していた（瞬間移動）ためです。

原因は4つありました。

1. **借り出し** … 始発駅に条件を満たす編成が無いと、近い留置場から
   在庫を付け替えていた（`FLEET_MAX_BORROW`）。
2. **返却** … 運用を終えた編成を「その車両所グループを受け入れる
   いちばん近い留置場」へ返していた。野洲で終わった明石の車両が
   高槻へ飛んでいた。
3. **留置場の無い駅の始発** … 加古川・大久保などが始発の列車は、
   西明石の編成をそのまま使っていた。
4. **延長運転で始発駅を更新していなかった** … 米原・京都で延長した列車の
   `startName` が前の駅のままで、記録上は瞬間移動に見えていた
   （車両の適合判定も違う線区で行われていた）。

直し方

* 列車を作るときの割り当ては **その駅にある編成だけ**（`noBorrow`）。
* 足りないときは、編成を持っている車両所から **送り込み回送**を出す
  （`js/27-operations.js` の `railInStock` / `backOrigin`）。
  回送は実際に線路を走るので行路がつながる。
* 返却は **いまいる場所の留置線**を優先する。そのために
  `FLEET_BASES` の受け入れグループを、実際にその駅まで来る車両に合わせた
  （明石の207系・321系は琵琶湖線の普通で野洲・米原・京都・姫路まで来る）。
* 片道で在庫が減る線区には **返却回送**を入れた（`checkStockBalance`）。
  放出の在庫が昼過ぎに0本になり、JR東西線の快速が 4本/時 → 1本/時 まで
  落ちていた。

実測（`node tools/harness.js --seed=20260922 tools/check_stockflow.js`）

| 指標 | 前 | 後 |
| --- | --- | --- |
| 行路のつながりのうち瞬間移動 | 25.7% (750/2921) | 3.3% (70/2099) |

残る3%ほどは、特急編成と機関車です。これらは車両所をまたぐ在庫として
持っているので（`js/24-service-rules.js` の `ExpressFleetPool` /
`FreightFleetPool`）、この見方では瞬間移動として出ます。

## 折り返しと番線

### 同一ホーム折り返し

折り返しのたびに番線が変わっていました。到着は下り線の着発線、
発車は上り線の着発線という作りで、折り返しの瞬間に必ず反対側の線路へ
移していたためです。

実際の運用では、折り返し列車は到着した番線にそのまま留まり、
種別・行先・列車番号だけが変わります。反対方向の線路へ移るのは
発車のときで、駅の渡り線を通ります。

そこで、渡り線のある駅では **その場で向きだけ変え**、
「発車のときに入る線路」を覚えておいて、最初の1ブロックを進むときに
転線するようにしました（`js/14-train-turnback.js` の `canTurnInPlace`、
`js/12-train-move.js` の `turnbackTrack`）。

| 指標 | 前 | 後 |
| --- | --- | --- |
| 折り返しで番線が変わらなかった割合 | 25.2% | 75.5% |

残りは、渡り線の無い駅・引上線を使う駅で、構内を移動して折り返すものです
（実際の入換動作にあたります）。

### 方転できない駅

* **大阪・新大阪** … ホームでは向きを変えられません。実物は東海道線の
  ホームの東西にある引上線へ引き上げてから方向を変えます。
  とくに丹波路快速のように **JR宝塚線へ向かう列車は、大阪のホームから
  宝塚線へ出る進路がありません**。宮原まで回送して方向を変え、
  戻ってから宝塚線へ入ります。
  この線路図は引上線そのものを閉塞として持たないので、
  「大阪に着いた折り返し列車は宮原へ回送する」という形で表しています。
* **尼崎** … 西側の引上線は、配線略図のとおり **4番・5番だけ**に
  つながっています。上り側と下り側で着発線が別なので、
  ホームのまま向きを変えることはできません。

## 分岐線の駅に実在しない番線が生えていた

## 駅名札の置き方

駅名札は「キャンバスのいちばん上」と「いちばん下」に置いていました。
本線だけを出しているときは実物と同じ形ですが、「全線」を選ぶと

* 本線の駅名が画面の最上部と最下部に離れて出る
* 分岐線の札と合わせて、同じ x に3つの名前が並ぶ
* 分岐線の札が、広がった番線やホームの帯に重なる

という状態になっていました。

いまは **線区（`TID_ROWS` の group）ごとに帯を求め、その帯の上と下に
その線区の駅名を置きます**。位置は「その駅が実際に使っている番線の
いちばん上・いちばん下」から決めるので、番線を上下に広げた大きな駅でも
ホームや列車表示に重なりません。分岐線に駅が無いインデックスでは
札を出さないので、同じ名前が3つ並ぶこともありません
（`js/41-tid-render.js` の `groupBands()` / `plateYsFor()`）。

当たり判定（`buildStationHits`）も同じ計算を使うので、札と反応する場所が
ずれません。`node tools/check_overlap.js` の重なりは 0 のままです。

## 転てつ器（渡り線・分岐・側線）の総点検

`js/40-tid-theme.js` の `TID_JUNCTIONS` が転てつ器の書き起こしです。
同梱の配線略図 `スクリーンショット (690).png` 〜 `(712).png`
（haisenryakuzu.net の東海道本線・山陽本線・北陸本線・湖西線・福知山線・
JR東西線のページ）を駅ごとに拡大して読み直し、
**渡り線の数・場所・向き・つないでいる線路**と、
**支線・車両基地の出入口の側と向き**を全線区ぶん直しました。

### 図の読み方（これを決めないと向きが逆になる）

1. **左右** … 図の左が上り方向（米原・大阪方）。
   `画像(711)` の「東海道本線 塚本方」、`画像(704)` の「東海道本線 元町方」、
   `画像(690)` の「北陸本線 坂田方」がいずれも左端にあることで分かります。
   Super-TID の画面も左が米原方なので、**図の左右＝画面の左右**です。
2. **上下** … `画像(704)` の兵庫駅で、兵庫の**南**にある和田岬線が
   図の**上**へ出ています。つまり図は「上が南・下が北」。
   日本は左側通行なので複々線の並びは北から
   上り外・上り内・下り内・下り外。北が下なので
   **図の上から 下り外・下り内・上り内・上り外** になります。
   これは Super-TID（`TID_ROWS`）と同じ並びです。
   桂川・島本・JR総持寺の島式ホームが内側線2本のあいだにあること、
   南草津・瀬田の相対式ホームが内側線の外側に付いていることが裏づけです。
   → 図で「いちばん上の線より上」に出る線は、画面でも上（`up: true`）。
3. **斜めの線がすべて転てつ器ではない** …
   駅の前後で線が斜めに折れているだけの所（ホームを置くために線路の
   間隔を広げている）は転てつ器ではありません。
   線の**本数が増える・減る**所だけが転てつ器です。
   おごと温泉・川西池田はこれを転てつ器と読み違えていました。

### 「置く場所」と「向き」の指定が画面と逆だった不具合

`TID_JUNCTIONS` の説明には
`"L"`（画面の左＝米原方）/ `"R"`（画面の右＝姫路方）と書いてあるのに、
描くときに `tidSide()` / `tidShape()` で左右を入れ替えていました。
そのため

* 4つめに側を書いた渡り線・支線 … 画面の**反対側**に描かれる
* 片渡りの `"l"` / `"r"` … 画面で**逆向き**に描かれる
* しかも4つめを省いたときの既定は入れ替えていなかったので、
  「省いた渡り線は画面左、書いた渡り線は画面右」と食い違っていた

という状態でした。実際に描いた絵で確かめた例として、
米原の「東海道本線 醒ケ井方」は `side:"L"` なのに彦根側（画面右）に

## 実物の配線で方転できない駅では折り返さない

利用者の指摘「遅れた列車が長岡京で勝手に折り返している」に対応したものです。

### 何が起きていたか

遅れの回復や詰まりの緩和のために、シミュレーターは
`SWITCHABLE_STATIONS` か `OVERTAKE_STATIONS` に入っている駅なら
どこでも自動で折り返しを作っていました。
ところがこの2つの表は

| 表 | 意味 |
| --- | --- |
| `SWITCHABLE_STATIONS` | 内側線と外側線を行き来できる駅（転線できる駅） |
| `OVERTAKE_STATIONS` | 待避（追い抜き）ができる駅 |

であって、「**向きを変えられる駅**」の表ではありません。
配線略図を読み直すと、長岡京にあるのは
「下り外↔下り内」と「上り内↔上り外」の片渡りだけで、
上下をつなぐ渡り線も引上線もありません。実物では方転できない駅です。

### 方転できる駅の条件（`js/03-stations.js` の `canReverseAt()`）

配線略図から読み取った次のどれかを持つ駅だけです。

1. **上り側の線路と下り側の線路をつなぐ渡り線**
   複線区間なら上下本線をつなぐ渡り線。複々線区間なら
   「下り内側線と上り内側線をつなぐ渡り線」。
   → `STATION_REVERSE_BY_CROSSOVER`（44駅）
   ★同じ向きどうしの渡り線（下り外↔下り内 など）では向きは変えられません。
2. **引上線** … 行き止まりの線に引き上げてから反対方向へ出る
   → `STATION_REVERSE_BY_DRAWUP`
3. **併設の車両基地** … 構内に入って方転する（`DEPOTS`）

全128駅のうち **50駅**が方転できる駅です。

### できる駅を止めてしまわないこと

利用者の指摘どおり、**吹田は方転できます**。

### 折り返しの代わりにすること

方転できない駅では、実際の運転整理と同じ順で扱います
（`js/14-train-turnback.js`）。

1. その駅に留置場があれば**入区**して運用を終える
2. 無ければ、前方でいちばん近い「方転できる駅」まで**延長運転**する
   （そこまでの区間に、いまの編成で入れることも条件）
3. それも無ければ車両所へ**回送**する／運用を終える

抑止（そのまま待たせる）だけで済む場合は、折り返しを作らずに待たせます。

### どこで止めているか

折り返しを作る経路すべてに入れました。どこから来ても
`js/14-train-turnback.js` の1か所を通るので、そこが最後の砦です。

| 場所 | 内容 |
| --- | --- |
| `js/14-train-turnback.js` | 折り返しの実行直前（**最後の砦**） |
| `js/11-train-core.js` | 見合わせ区間手前での自動折り返し（長岡京の件） |
| `js/27-operations.js` | `preferTurnback()`（終着駅での折り返し） |
| `js/16-train-adjust.js` | 混雑時の間引き・行先の打ち切り |
| `js/03-stations.js` | `canTurnBackOnPlatform()`（同一ホーム折り返し） |

## 乱数の種による詰まりの崩壊を直した

同じコードでも乱数の種によって、詰まり具合が 14% と 44% に分かれていました。
種を変えても安定するように、原因をたどって直したものです。

### たどり方

1分以上動けない列車がいちばん多い所を駅＋線路ごとに数えました
（`tools/.tmp/diag_jam.js` にあたるもの）。どの種でも上位は

```
尼崎 Fukuchi_Down / 新三田 Fukuchi_Down / 川西池田 Fukuchi_Down /
塚口 Fukuchi_Down / 尼崎 Tozai_Up / 京橋 Tozai_Up / 放出 Tozai_Up
```

で、**JR宝塚線の下りと JR東西線の上りが飽和**し、
尼崎で本線と着発線を共有しているために、そこから
`尼崎 Down_Out → 大阪 → 新大阪 → 高槻 → 茨木` と
**本線の下りへ波及**していました。

### 直した4つの原因

1. **線区の端に着いた列車が終点扱いにならなかった**（いちばん大きい原因）
   `js/12-train-move.js` の「線路の無い区間へは進ませない」処理が
   `if (this.state !== "stopped")` という条件付きで、
   状態が `holding` の列車は終点扱いになりませんでした。
   `holding` のあいだ `move()` は呼ばれないので、いちど抑止に入ると
   二度と終点扱いになりません。実測では
   `放出 dest=放出 holding` が 5790 tick、`新三田 dest=新三田 holding` が 4630 tick。
   終点扱いを `Train.prototype.endOfLineStop()` にまとめ、
   抑止の経路（`js/11-train-core.js`）からも呼ぶようにしました。
   山科のように「転線すれば先へ進める」場所で打ち切らないよう、
   *自分の終点に着いている* か *前方に線路が無いまま10分以上動けていない*
   のどちらかに限っています。

2. **分岐線の本数の目安が効いていなかった**
   `js/09-spawner-branch.js` の判定が
   `ty !== "普通" || !ttOverBudget(…,"fukuchi",…) || !ttOverBudget(…,"tozai",…)`
   と `||` でつながっていて、
   *快速をまったく数えていない* / *宝塚線が目安を超えていても東西線に余裕が
   あれば作り続ける* 状態でした。線区ごと・種別ごとに見るよう直しました。
   あわせて「その線区の入口付近で列車が止まっているときは始発を出さない」
   （実際の指令と同じ扱い）を足しています。

3. **本線からの直通に目安が効いていなかった**
   本線の列車に「松井山手行き」などの行先を与える経路に目安が無く、
   JR東西線の普通が目安10本に対して**在線24.7本**まで増えていました。
   `js/08-spawner-mainline.js` の `sanitizeDestination()` で、
   分岐線がこんでいるときは直通を入れないようにしました。

4. **終着に着いた列車が目安を無視して折り返していた**
   `tryConvertDeadhead()` がまず折り返しを試すため、
   目安を超えていても走り続けていました。`preferTurnback()` に
   「目安の3割超で、かつ折り返した先に続く列車がいるなら折り返さない」
   を足しました。

さらに、片方向の詰まりで反対向きが餓死しないように
「その向きに列車がほとんどいないときは目安を超えていても1本出す」
（最低運転）と、留置場の出区待ちの上限（20分待ち → 11分）を入れています。

### 2. 指令パッドの着発番線変更が効かない

| 原因 | 何が起きていたか |
| --- | --- |

直し方（`js/13-train-hold.js` の「着発番線の変更」）

* 予約のときに、向き・通過済み・行先より先か・配線の進路・レーンの有無を確かめ、

* 駅へ進入するときに、指定の線路・レーンへ入れる（`move` / `checkHold` が同じ判定）。
* すでにその駅に居るなら、その場で構内の転線をする。
* 指定の番線がふさがっているあいだは手前で待つ。5分空かないときは予約を取りやめ、
  通常の番線に入れる（待ち続けて線区を止めない）。結果は運転指令の記録に残る。
* 予約の取り消しもできる。

走行中の75本に別の番線を予約して、**72本が指定どおりの線路・番線に入り**、
3本は指定の番線が5分以上ふさがっていたため取りやめ（理由つき）。
通過済み・反対方向・無い番線は断り、停車中の列車はその場で転線する。

### あわせて直した不具合

* **折り返しの行先が京都に書き換わる** … 折り返しのときの「行先が始発駅と同じなら代わりの行先にする」
  判定が、折り返す駅ではなく**前の列車の始発駅**と比べていた。姫路発相生行きが相生で折り返して
  姫路行きになると「後方」とみなされ、京都行きに書き換わっていた（全線で起きうる）。
* **逆向きに走る回送** … 着いた番線の都合で下り線に入った上り列車が、そのまま下り線を逆に走ることがあった。
  線路の向きと列車の向きが食い違ったら、同じ側の正しい線路に移す（`fixDirectionTrack`）。
* **分岐線で行先の短縮が効きすぎる** … 「高槻まで」「草津より先」のような短縮を駅の番号の大小で判断していて、
  分岐線（学研都市線など）の駅が本線の駅に見えていた。本線の中の行程だけにした（`isMainlineTrip`）。
* 留置場の在線リストとレーンの登録の食い違い（`freeOwnLane` にそろえた）。

### 1. 輸送障害の種類と場面を増やした（`js/33-incident-scenarios.js`）

  合計 60 は以前のまま。

  | 系統 | 足した種類 |
  | --- | --- |
  | 人身事故 | 触車（ホーム上の旅客と接触） |
  | 架線・電力 | 落雷によるき電停止 |

### 3. 長引く見合わせのあとの運転再開を作り直した（`RecoveryControl`）

以前は区間を駅間ごとに「開通待ち」にし、確認列車を「1本進める」で1本ずつ通す形でした。
列車が多いと同じ操作を何十回も繰り返すことになるので、次の形にしました。

1. **見合わせが始まった時点で、区間の中の列車をすべて抑止する**（大雨・大雪・人身事故の重いもの）。
2. 見合わせを**正式に解除**する（線路の見合わせは解ける）。区間と、その手前に詰まっている列車は
   **1本ずつの抑止として残る**。区間の中の駅から新たに発車しようとする列車も、順番が来るまで待つ（解除から30分まで）。

### 4. 深夜の本数（`js/10-timetable.js` の `TT_SERVICE_END`）

**原因** … 3つが重なっていた。

1. 終点で「22:45 を過ぎたら折り返さずに列車を消す」と一律に決めていた。
2. 留置場で出区を待つ列車を「23時になったら消す」としていたので、放出・新三田の留置場から出る学研都市線・JR宝塚線の
   23時台の列車が走らなかった（分岐線の列車の多くは留置場から出る）。
3. 0時台は時間帯「深夜」として全部 0本。大阪 0:00 の新快速・0:10 の普通のような終電が無かった。

**直し方** … 線区ごとの**終電の時刻**を時刻表から決め（本線 0:15・JR東西線/学研都市線 0:15・JR宝塚線 0:00・湖西線 23:45・姫路以西 23:54）、

* それまでは終点で折り返す。そのあとは、その駅の留置線 → 近くの車両所への回送 の順で夜の留置に入る（消すのはどちらもできないときだけ）
* 留置場の出区待ちは、出区の時刻が終電より前なら出す
* 時間帯「終電」(0:00〜0:45) を足した（本線の普通・新快速）
* 分岐線の始発は終電のあとは出さない（以前は時刻で止めていなかった）
* 列車を消したとき・留置場で夜を明かしたとき、編成を**その留置場**に置く（以前は行先の近くの車両所へ瞬間移動していた）

| 旅客列車の在線（種 3・42・7・99・20260922） | 直す前 | 直した後 |
| --- | --- | --- |
| 0:00 | 69〜94本 | 119〜140本 |
| 0:30 | 47〜64本 | 87〜113本 |

実際の時刻表では 0:30 ごろに各線の終電が出るので、1時を過ぎると本線の列車は終点へ向かう最後の列車だけになります。

### 7. 配線で折り返せる駅をすべて使う（`canReverseAtDir`・`terminableStations`）

**甲子園口（698）** … 折返線（2番）は西宮方が行き止まりで、**立花方で下り内から入り、立花方で上り内へ出る**。
線路図では、折返線が下り内にしかつながっておらず、別に下り内と上り内を直接つなぐ斜めの線を描いていた（実物に無い）。
折返線の取付線を上り内にもつなぎ、直接の渡り線は描かないようにした（`STATION_STUB_LANES` の `exitTo`）。
運転の判定も、折返線に居る列車だけが折り返せる・上り列車は甲子園口で折り返せない、にした。

**吹田（696）** … 東淀川方（大阪方）の、下り内↔上り内の**両渡り**。大阪方から来た上り列車が大阪方へ折り返せる。
複々線の中の駅でも、吹田止まりの列車は下りホームにも直接入れる（`STATION_CROSS_ARRIVE_QUAD`）。
京都方から来た下り列車は吹田では折り返せない（渡り線が大阪方ののどにしか無い）。

**全駅** … 「その駅のどこかで向きを変えられるか」（`canReverseAt`）に加えて、**着いた向きで折り返せるか**
（`canReverseAtDir`）を持たせた。渡り線がホームの片側ののどにしか無い駅（須磨・芦屋・神戸・吹田・甲子園口など）は、
渡り線の側から着いた列車だけ折り返せる（`STATION_ARRIVAL_CROSSOVER` の書き起こしから決まる）。
引上線・車両基地・単線上の1線の駅はどちら向きでもよい。折り返しを作るすべての所（折り返しの実行・見合わせ区間の手前の
自動折り返し・混雑の間引き・深夜の行先の短縮・指令の行先変更・回送への変更）がこれを通る。

**指令の行先変更** … 候補は決め打ちの表をやめ、線路の定義から作る（`dispatchDestinationCandidates`。旅客向け画面と Super-TID で同じ）。
甲子園口・吹田・徳庵・長尾・JR三山木・祝園 など、折り返せる 74駅（＋線路図の外の行先）が選べる。
その向きに着いて折り返せない駅（京都方から来た下り列車の「吹田止まり」など）は、理由つきで断る。

**輸送障害・指令連絡** … 「手前で折り返し」「打ち切って入区」の駅を、以前は `SWITCHABLE_STATIONS`（内側線と外側線を
行き来できる駅＝長岡京など方転できない駅も入る）から選んでいた。前方で**その向きに折り返せる駅**から選ぶ（`commAheadTurnback`）。

### 乱数を固定して比べる

シミュレーターには乱数が入っているので、同じコードでも走らせるたびに
結果が変わります。実測すると「1分以上動けない列車の割合」は、同じコードで
**9.9% 〜 22.0%** まで振れました（人身事故が起きた回で跳ねる）。
調整の前後を比べるときは `--seed` で同じ1日を走らせてください。

```
node tools/harness.js --seed=20260922 tools/check_convoy.js
```

★ソースを読み込む前に差し替えています。`js/39-boot.js` は読み込みの時点で
`GameSystem` と `Spawner` を作り、その中で乱数を使うためです。

分割前のコードと比べたいときは、先に基準値のソースを取り出します。

```
python tools/extract_baseline.py                        # gitから分割前のコードを取り出す

node tools/harness.js        tools/check_baseline.js    # 分割後の生成本数
node tools/check_logic_diff.js                          # どのメソッドを変更したかの一覧
```
